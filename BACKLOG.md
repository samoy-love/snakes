# BACKLOG

Этот файл — единый беклог задач по итогам ревью проекта `windsurf-project-7`.

Цели:

- Привести проект к стабильной **многопользовательской** архитектуре (server-authoritative) и удобной для развития структуре.
- Сделать деплой воспроизводимым: **nginx + docker-compose**.
- Включить наблюдаемость: **Prometheus + Grafana** с **персистентными volume**.
- Повысить скорость разработки (TTM) и удобство правок (в т.ч. нейросетями): разрезать монолиты, изолировать протокол.
- Добавить минимальные тесты/CI, чтобы не ломать протокол/WS-флоу.

Обозначения:

- Приоритет: **P0** (критично/сначала), **P1** (следующим), **P2** (когда будет время)
- DoD = Definition of Done (критерии готовности)

---

## EPIC A — Платформа деплоя и релизов (Docker/Compose/nginx) (P0)

### A1. Dockerfile для Go-сервера

**Почему**: чтобы сборка/запуск были одинаковыми локально и на сервере.

**Подзадачи**:

- Сделать multi-stage Dockerfile (builder + runtime).
- Пробросить конфигурацию через env:
  - `PORT`
  - `ROOM_LIMIT`
  - `WS_ORIGINS` (или аналог)
  - `LOG_LEVEL`
- Проложить порт и команду запуска.

**DoD**:

- `docker build .` проходит.
- `docker run -p 3000:3000 ...` запускает сервер и он отвечает на `/`.
- В runtime-образе нет исходников/кэша сборки (только бинарь и то, что нужно).

---

### A2. docker-compose.yml: game + nginx + prometheus + grafana

**Почему**: чтобы одной командой поднимать прод-стек.

**Подзадачи**:

- Добавить сервис `game`.
- Добавить сервис `nginx` (reverse proxy).
- Добавить сервис `prometheus`.
- Добавить сервис `grafana`.
- Настроить сети compose (одна общая network).
- Добавить volumes:
  - `prometheus_data` для `/prometheus`
  - `grafana_data` для `/var/lib/grafana`

**DoD**:

- `docker compose up -d` поднимает все сервисы.
- При `docker compose down` и новом `up`:
  - данные Grafana (дашборды/настройки) не пропадают;
  - данные Prometheus не пропадают.

---

### A3. Nginx-конфиг для compose

**Почему**: корректный WS upgrade, кеширование статики, закрытие служебных эндпоинтов.

**Подзадачи**:

- Проксировать `location = /ws` на `game`:
  - `proxy_http_version 1.1`
  - `Upgrade`/`Connection` заголовки
  - `proxy_read_timeout` (длинный, например 3600)
- Статику:
  - либо раздавать nginx’ом (маунт `./public`),
  - либо проксировать `/` на Go (не идеал, но приемлемо).
- Закрыть `/metrics`:
  - allowlist по IP или basic-auth (рекомендуется).

**DoD**:

- WebSocket соединение не отваливается из-за таймаутов.
- `/metrics` недоступен извне без авторизации/allowlist.
- Статика загружается корректно.

### A5. GitHub Actions: тесты + сборка + push Docker image в GHCR

**Почему**: автоматический выпуск новых версий.

**Подзадачи**:

- Workflow `ci.yml`:
  - `go test ./...`

**DoD**:

## EPIC D — Протокол, совместимость и идентичность игрока (P0)

### D1. Явная версия протокола

**Почему**: чтобы не ломать клиентов при изменении бинарного формата.

**Подзадачи**:

- Сервер шлет `proto` в `hello` и/или `init`.
- Клиент проверяет и показывает ошибку при несовместимости.

**DoD**:

- При несовпадении версий клиент показывает понятный экран/сообщение.

---

### D2. `clientId` вместо IP как ключ профиля

**Почему**: IP не уникален (NAT), меняется, ломает "профиль".

**Подзадачи**:

- Клиент:
  - генерить `clientId` один раз
  - хранить в localStorage
  - отправлять на сервер (например `identify`).
- Сервер:
  - хранить/использовать `clientId` как `profileKey`
  - IP оставить как атрибут (для модерации/аналитики)

**DoD**:

- При переподключении по тому же `clientId` профиль сохраняется.

---

### D3. Input seq + ack

**Почему**: диагностика лагов и основа для client prediction.

**Подзадачи**:

- Клиент шлет `input: {dir, seq, t}`.
- Сервер сохраняет `lastSeqApplied`.
- Сервер отвечает `ack` (JSON или как часть бинарного пакета).

**DoD**:

- В логах/метриках можно отследить задержку ack.

---

## EPIC E — Производительность сервера (P1)

### E1. Убрать аллокации в hot-path `Room.step()`

**Почему**: снизить давление на GC.

**Подзадачи**:

- Пуллить `map[*Client]*pooledData`.
- Максимально reuse временные слайсы/буферы.

**DoD**:

- Heap/alloc профили показывают уменьшение allocs на тик.

---

### E2. Сократить работу под `r.mu`

**Почему**: уменьшить tail-latency.

**Подзадачи**:

- Под `r.mu`:
  - симуляция
  - фиксация "снимка" данных
- Вне `r.mu`:
  - сериализация ROI/ивентов/миникарты

**DoD**:

- Tick latency становится стабильнее на нагрузке.

---

### E3. Политика backpressure

**Почему**: не перегружать клиентов и не копить очереди.

**Подзадачи**:

- Явно определить:
  - какие сообщения `drop=true`
  - какие должны быть reliable (init/error/left)
- Метрики dropped/queue depth.

**DoD**:

- При перегрузе сервер не умирает, клиенты деградируют предсказуемо.
